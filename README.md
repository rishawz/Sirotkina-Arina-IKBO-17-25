# Инструмент визуализации графа зависимостей (NuGet)

Практическая работа № 2, дисциплина «Конфигурационное управление»,
вариант 25. Статус: этап 5 из 5 (визуализация).

## 1. Общее описание

CLI-приложение на Python 3.9+ (только стандартная библиотека). Источник
параметров - опции командной строки. Приложение:

- получает прямые зависимости пакета NuGet заданной версии из `.nuspec`
  по URL репозитория (без менеджеров пакетов и сторонних библиотек);
- строит граф зависимостей с учётом транзитивности рекурсивным DFS,
  с ограничением глубины, фильтром имён по подстроке и обработкой
  циклов;
- умеет работать с тестовым репозиторием из файла (пакеты `A`, `B`, ...);
- выводит на экран описание графа на языке PlantUML и, по запросу,
  зависимости в виде ASCII-дерева.

Структура: `src/depgraph` - исходный код, `tests` - модульные тесты,
`examples` - тестовые репозитории и локальный NuGet-репозиторий,
`run.sh` и `Makefile` - запуск.

## 2. Функции и настройки

| Опция | Описание |
|-------|----------|
| `-p`, `--package` | имя анализируемого пакета (обязательна) |
| `-r`, `--repo` | URL репозитория NuGet или путь к файлу тестового репозитория |
| `-t`, `--test-mode` | режим работы с тестовым репозиторием |
| `-V`, `--version` | версия пакета (обязательна вне тестового режима) |
| `-a`, `--ascii-tree` | дополнительно вывести зависимости в виде ASCII-дерева |
| `-d`, `--max-depth` | максимальная глубина анализа, по умолчанию 3 |
| `-f`, `--substring` | не учитывать пакеты, в имени которых есть подстрока |

Если `--repo` не задан вне тестового режима, используется
`https://api.nuget.org/v3-flatcontainer/`. Ошибки параметров (имя, версия,
URL, файл, глубина) и ошибки получения данных выводятся в stderr, код
возврата - 2.

**Получение данных** (`nuget.py`). По протоколу NuGet v3 (Package
Content, «flat container») запрашивается
`{repo}/{id}/{version}/{id}.nuspec` (id и версия в нижнем регистре).
Используются только `urllib` и `xml.etree`. Зависимости всех групп
`targetFramework` объединяются, повторы по имени отбрасываются
(остаётся первое вхождение).

**Версии транзитивных пакетов** (`versions.py`, `nuget_source.py`).
Берётся нижняя граница диапазона из nuspec (NuGet выбирает минимальную
подходящую версию); если границы нет - последняя стабильная версия из
`{repo}/{id}/index.json`. Пакет раскрывается с версией из диапазона,
с которым он встретился первым.

**Граф** (`graph.py`). Рекурсивный DFS. Узлы на глубине `--max-depth`
не раскрываются (глубина корня - 0). Пакеты, в имени которых есть
подстрока `--substring` (без учёта регистра), в анализе не участвуют;
корневой пакет не фильтруется. Циклы: узел повторно раскрывается, только
если до него найден более короткий путь, поэтому обход всегда
завершается; ребро, замыкающее цикл, остаётся в графе. Глубокие цепочки
ограничены лимитом рекурсии Python - при его превышении выводится ошибка
с советом уменьшить `--max-depth`.

**Тестовый режим** (`testrepo.py`): `--test-mode --repo файл`. Формат
файла - строка `A: B C` (A зависит от B и C), `D:` - пакет без
зависимостей, имена - заглавные латинские буквы, строки с `#` -
комментарии. Версия не нужна.

**PlantUML** (`plantuml.py`). Каждый пакет - `rectangle`, зависимость -
стрелка `A --> B` (A зависит от B), корень выделен цветом. Описание
можно вставить в [plantuml.com](https://www.plantuml.com/plantuml) или
отрисовать локальным `plantuml`.

**ASCII-дерево** (`tree.py`). Узел раскрывается один раз; повторное
появление узла с зависимостями (общая зависимость или цикл) помечается
`(*)` и не раскрывается.

## 3. Сборка и тесты

Сборка не требуется (нужен только Python 3.9+).

```
./run.sh <опции>              # запуск
make run ARGS="<опции>"       # то же через Makefile
make test                     # модульные тесты (unittest)
```

## 4. Примеры использования

Реальный репозиторий (нужен доступ в интернет):

```

```

## 5. Сравнение со штатными инструментами

Штатные средства .NET показывают зависимости уже восстановленного
проекта, а не одного пакета из репозитория:

```
dotnet list package --include-transitive
dotnet nuget why <проект> <пакет>     # .NET SDK 9+
```

Для сравнения нужен .NET SDK и доступ к nuget.org: создайте проект
(`dotnet new console`), добавьте пакет (`dotnet add package <имя>
--version <версия>`) и сопоставьте вывод с `./run.sh -p <имя> -V <версия>
-d <глубина> -a`. Ожидаемые причины расхождений:

1. **Целевой фреймворк.** `dotnet` берёт зависимости одной группы
   `targetFramework`, подходящей проекту; данный инструмент объединяет
   все группы, поэтому в графе может быть больше пакетов (например,
   `Demo.Compat` из группы `.NETStandard2.0` в `Demo.App`).
2. **Выбор версий.** `dotnet` разрешает конфликты версий (побеждает
   ближайшая к корню, берутся максимальные нижние границы), инструмент
   берёт нижнюю границу диапазона у первого встреченного вхождения и
   не пересматривает её.
3. **Метапакеты и платформенные зависимости.** `dotnet` не показывает
   пакеты, входящие в целевой фреймворк (например, `NETStandard.Library`
   при `net8.0`), а инструмент покажет их, если они есть в nuspec.
4. **Глубина и фильтр.** Опции `--max-depth` и `--substring` у штатных
   инструментов нет: они выводят граф целиком.
5. **Вид вывода.** `dotnet list package` печатает плоский список без
   рёбер; граф, ребра и порядок обхода DFS видны только здесь.
6. **Предрелизные версии и диапазоны без нижней границы** выбираются
   по-разному (инструмент берёт последнюю стабильную версию).

Результаты запуска на реальных пакетах (например, `Newtonsoft.Json`,
`Serilog`, `Microsoft.Extensions.Logging`) нужно получить на машине с
доступом в интернет и .NET SDK; в этом репозитории демонстрации выше
выполнены на локальном mock-репозитории и на тестовых файлах.
